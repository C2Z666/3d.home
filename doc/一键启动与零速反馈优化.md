# 一键启动与零速反馈后续优化

在 Orin 当前仓库执行：

```bash
cd /home/robot/zhangzhang/3d.home
bash start.sh
```

仅检查状态：`bash start.sh --status --wait 10`。默认等待60秒，机器人SDK地址默认192.168.168.168，可用 `--robot-ip` 指定。网页地址为 http://192.168.168.100:8767/?scene=old 。

入口调用 scripts/start_stack.py：核对底层前相机/前雷达/雷达IMU正在输出，复用当前仓库已有网页与SDK bridge，启动 FAST-LIO、融合定位、扫描投影、网页专用的 /d1/preview 预览规划器和执行用 Nav2。原厂传感器驱动及 Zenoh 路由由机器狗已有系统服务管理；脚本不会重启这些系统服务。日志/PID保存在当前仓库 work，状态写入 work/start_stack_status.json。脚本没有速度发布者，不发送姿态或导航目标；bridge连接可能持有控制权，但导航仍须网页确认。已有导航任务/速度发布者时拒绝本轮启动，避免干扰当前控制。已启动的服务在退出后继续运行。

FAST-LIO 参数从既有 fastlio_live/d1_airy_live.yaml 原样复制到 config/fastlio_live.yaml，使用同一已安装程序，不改变雷达、IMU、外参和滤波参数。新的启动锁、PID及标准输出日志放在本仓库，sensor_stack.py 的启动/状态/停止路径同步到本仓库。

若输出 NOT_READY，表示服务保留运行，但数据或导航生命周期尚未就绪，不能把它当作成功导航。首次开机需要有效视觉匹配建立 map 对齐；FAST-LIO只能连续提供局部里程计，不能凭空知道新启动后的地图位置。没有首次视觉对齐时等待是必要条件，与已有对齐后的短暂视觉丢失继续 ODOM_ONLY 不同。保持机身静止并让相机看到建图时的特征，等待自动初始化；不要复制上一次开机的 map→odom 变换，也不要仅为使页面变绿放宽匹配门槛。状态打印视觉拒绝原因和有效匹配数量。

## 报告对应的优化顺序

依据《零速SDK反馈与导航算法影响测试报告》：SDK前向反馈0.019～0.026m/s并不参与bridge速度计算；反馈范围本身尚不能证明真实滑移。当前逐轴0.03门槛虽能通过，但前向余量只有约0.004m/s，值得消除临界抖动。

1. 先扩展独立于导航任务的只读同步采样：SDK状态/序号/新鲜度、实际Move分量与写入结果、nav_odom增量和速度、map对齐修正、外部视频参照。已实现的任务诊断无法覆盖无任务期间的完整零速基线；没有bridge回显字段时必须明确缺失，不能用监督器发布值代替。
2. 统一任务启动、停稳、重定位准入的运动证据模块。输出 STOPPED/MOVING/UNKNOWN 及具体原因；检查新鲜度、连续时间窗，并区分SDK反馈不一致与真实位移。使用nav_odom连续位置/朝向变化作为运动证据；map位姿用于目标复核，融合修正不能算作底盘真实滑移。时间窗同时观察净位移和窗内变化，避免往返运动净位移为零却误报停稳。
3. 重复确认外部静止后，按姿态/温度记录零速分布，用中位数和分位数估计噪声，设置进入/退出迟滞。若证实仅SDK偏置，可在运动判定中使用标定后的反馈残差，保留原始值和上限保护；不能将偏置从控制指令中直接扣除。此阶段先记录“新判定结果”，与旧判定并行比较，不立即接管控制。
4. 将立即发零、停止确认和目标完成分别处理。已经到位置后调整朝向，随后停稳复核；仅SDK瞬时越过0.03不立即消耗位置恢复次数。若里程计/位姿表明确有移动，继续停车并给出真实滑移诊断，不能靠放宽目标阈值伪装成功。超时需明确打印当前阻塞源。
5. 单独验证长时间TF中断后的Nav2恢复、低角速死区及终点角度收敛。它们不能都归因于SDK零速偏置。每轮只修改一项控制策略并对照诊断记录，保留现有独立恢复预算、原任务总时限和碰撞检查。

原报告温度告警单独记录，目前没有证据证明其造成零速反馈或导航失败。本轮只增加启动能力，不调整停稳阈值、速度上限、融合权重或SDK补偿。


本次启动实测：首次等待有效视觉匹配后已进入FUSED；FAST-LIO、融合定位、扫描投影均只有一个发布者，Nav2五个生命周期节点全部active，SDK控制权/新鲜度/零指令正常，网页地图与相机接口HTTP 200。重复运行复用已有服务；退出的SDK桥能够重新启动。未发送导航目标或姿态命令。

原厂 `/front_camera/image` 图中登记两个端点：`robot_camera` 与 `image_decode`。仅根据端点数量不能证明正在交替发送不同图像；本轮不修改或停止原厂服务，将其作为 sensor_duplicate_topics 诊断提示。核心里程计/融合定位/扫描/SDK重复发布仍阻止启动检查成功。后续视觉诊断应进一步按publisher GID核对实际帧来源、采集时间戳和重复帧，避免把原厂双端点直接当作定位算法故障。


启动验收补充：网页预览连接 /d1/preview/compute_path_to_pose，代价地图来自 /d1/preview/global_costmap/get_costmap。它们与执行用 Nav2 分开，必须启动 scripts/run_planner_preview.sh。start.sh 已补齐这一服务，READY 要求预览动作服务在线且网页 /preview-costmap 可读；不再仅凭定位和执行Nav2就绪判断启动成功。现场通过 /preview-plan 只读预览实际返回路线，未启动导航。
